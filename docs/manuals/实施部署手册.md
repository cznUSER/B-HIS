## 1. 重要边界

本手册是开发、隔离测试和获准现场环境的实施基线。下列动作必须先取得用户明确授权并建立任务卡：

- 生产部署或试点上线。
- 真实患者/收费数据迁移。
- 生产数据库结构变更。
- 生产备份恢复、回滚和停服。
- 对医院人员或第三方系统的外部通知/操作。

文档、命令和配置示例不得包含真实密码、DSN 口令或患者明细。

## 2. 部署形态

当前推荐形态为 Windows 本机 Host 分端口提供网站和同机 API：网站监听 `127.0.0.1:8888`，`/` 提供嵌入 Vue SPA；Go API 监听 `127.0.0.1:9999`，提供 `/api/v1` 和 `/health`。网站将 `/api` 与 `/health` 转发到 Go API，`logs/` 保存运行日志。

SQL Server 是正式运行时数据库；达梦接口仅为预留，不在本手册中启用。开发时 `web` 目录可以独立运行 Vite，但那是开发/验收入口，不是现场部署形态。

## 3. 环境准备

### 主机和软件

- Windows 主机，具备运行 B-HIS Host 的账户权限。
- Go 工具链用于从源码构建；Node.js/npm 用于构建网站资源。
- SQL Server 2022 或项目确认兼容版本，目标数据库名为 `BHIS`。
- 可访问的日志目录；日志目录不应进入 Git。
- 浏览器可访问 Host 地址；现场防火墙仅开放批准的监听端口。

### 配置和秘密

优先使用安装目录外的 `config.local.yaml` 或环境变量。至少核对 `BHIS_DB_DRIVER=sqlserver`、`BHIS_DB_DSN=sqlserver://<user>:<password>@<host>:1433?database=BHIS&encrypt=disable`、`BHIS_JWT_SECRET=<部署环境秘密>`、`BHIS_API_ADDR=127.0.0.1:9999`、`BHIS_WEB_ADDR=127.0.0.1:8888` 和 `BHIS_LOG_DIR=<安装目录>\logs`。

示例中的尖括号值必须替换；不得把真实值提交仓库、写进手册或放进命令历史。DSN 和口令只存于受控配置或环境变量。

## 4. 构建和打包

在 `E:\B-HIS\web` 执行 `npm ci`、`npm run check`、`npm run build:demo`。`build:demo` 应生成关闭 Mock、请求同源 `/api/v1` 的网站资源。构建完成后确认 `internal/webui/assets/` 的嵌入资源来自本次构建，不把旧包当成新版本。

在仓库根目录执行 `go test ./...`、`go vet ./...` 和 `go build -o bin\\b-his-host.exe .\\cmd\\host`。交付记录必须包括工程名、版本/提交、exe 路径、打开后的第一眼页面、是否需要登录和是否需要再点入口。若为 Demo 或会话包，另遵守项目规定的会话目录和出包脚本。

### GitLab 自动检查

仓库根目录的 `.gitlab-ci.yml` 定义分支、合并请求和标签流水线的基础检查：

- `diff:check`：对本次提交差异执行 `git diff --check`，检查空白和冲突标记等问题。
- `go:test`：执行 `go test ./... -count=1`。此 job 主动清除 `BHIS_DASHBOARD_TEST_DSN`，不连接 SQL Server；SQL 集成测试在缺少 DSN 时按测试约定跳过。
- `go:vet`：执行 `go vet ./...`。
- `web:quality`：执行 `npm ci`、`npm run check` 和 `npm run build`。这些检查使用仓库内脚本，不需要真实 API 或数据库凭据。CI 的 `build` 是通用前端构建；发布嵌入资源仍按本节前述步骤执行 `build:demo` 并核对产物。

SQL Server 集成测试位于 `sql:integration` 手动作业，不属于默认流水线。只有在 GitLab 项目/流水线变量显式设置 `BHIS_SQL_INTEGRATION=true` 后，流水线才显示该手动作业；启用后它是必须人工执行并通过的流水线门禁。启动前必须同时设置 `BHIS_DASHBOARD_TEST_DB=BHIS_PHASE2_TEST_20261015` 和指向该库的 `BHIS_DASHBOARD_TEST_DSN`。脚本要求 DSN 使用 `sqlserver://`，服务器精确为 Code A 隔离测试端点 `192.168.1.138:53151`，且唯一的 `database` 参数精确等于 `BHIS_PHASE2_TEST_20261015`，随后执行完整 `go test ./internal/store/mssql -count=1`，覆盖该包的 MSSQL 集成与普通测试。`resource_group` 会串行化所有使用该隔离库的 CI 作业。激活前须将 DSN 凭据设为受保护 CI 变量，并在 GitLab 侧将作业限制到可访问 Code A 的受控 runner；凭据不得写入仓库或日志。不得将生产、现场或其他共享业务库用于该作业。

证据边界（截至 2026-10-17）：提交 `64b456e44bd6c7ce5f0fbc97a8d6e8b48c785ec6` 的认证 GitLab CI Lint 返回 `valid=true`、0 个错误，并模拟出 `diff:check`、`go:test`、`go:vet`、`web:quality` 四个默认 job；SQL job 因未设置 `BHIS_SQL_INTEGRATION=true` 而未列入。Runner 上线前，pipeline `#38` 因没有匹配 Runner 而失败。Runner 上线后新建 pipeline `#39`：`diff:check` 在 Code A Runner 上通过；`go:test` 与 `go:vet` 因容器连接 `proxy.golang.org:443` 被拒而失败；`web:quality` 因前置 quality 阶段失败而跳过。该次流水线没有触发手动 SQL 集成作业。因此 Runner 分配、拉起 CI 镜像和运行任务链路已验证，但 pipeline `#39` 当时未全绿；Go 模块代理故障的修正和后续验证见下文。

Runner 现状：GitLab CE `19.5.0-ce.0` 运行在 Code A Docker Desktop/WSL2 上。Code A 的 WSL2 全局上限设为 `24 GiB`、交换空间 `8 GiB`，Docker Linux 引擎实际可用内存约 `23.47 GiB`。GitLab Runner `19.5.0` 作为 Windows 自动启动服务运行，使用 Docker executor 连接同机 Linux Docker 引擎；项目 Runner `#1` 名称为 `Code A Docker Runner`，锁定在 `root/b-his`，启用 untagged 任务，标签为 `code-a,docker,linux`。全局并发与单 Runner 并发均为 `1`，每个 job 限制 `4 GiB` 内存、`4` 个 CPU、`privileged=false`；只允许当前 CI 声明的 Alpine、Go、Node 三种镜像。

Docker Hub 在 Code A 上无法直接解析/访问，因此当前 CI 基础镜像已从 AWS ECR Public 的 Docker Library 官方镜像缓存到本地，并保留 `.gitlab-ci.yml` 使用的原镜像标签；Runner 使用 `if-not-present` 拉取策略。GitLab Runner helper 镜像已从 GitLab Container Registry 拉取并缓存在本地。镜像标签更新或新增镜像时，需先通过获准的镜像源同步到该 Docker 引擎；否则 job 会在准备镜像阶段失败。Runner authentication token 仅保存在 Code A 的 `E:\GitLabRunner\config.toml`，文件 ACL 仅授权 `SYSTEM` 和本机管理员，不写入仓库、聊天、命令行或 CI 变量。该 Runner 只处理本项目；启用 SQL 集成前仍须配置受保护 DSN，并确认 Runner 可访问 Code A 隔离测试库 `BHIS_PHASE2_TEST_20261015`，不得触达生产或共享业务库。

Go 模块代理排障（2026-10-17）：Code A 到 `proxy.golang.org:443` 超时；Code A 主机访问 `https://goproxy.cn` 返回 HTTP 200，Runner 使用的 `golang:1.22-bookworm` 容器通过该代理成功下载项目 `go.mod` 中全部直接依赖及其模块图。`.gitlab-ci.yml` 全局设置 `GOPROXY=https://goproxy.cn`，只对 Go 命令产生作用；保留 Go 默认校验和验证，不配置 `direct` 回退。

流水线 `#40`（提交 `6e96edf`）确认 Go 模块已从 `goproxy.cn` 成功下载；`go:test` 与 `go:vet` 随后因该提交缺少 `domain.Diagnose` 和 `domain.InventoryLedgerEntry` 类型定义而在编译阶段失败，已不是代理连接错误。提交 `5ff7678` 已补入这两个类型。流水线 `#41` 的 `diff:check` 通过，两个 Go job 再次成功下载全部模块，但编译时发现 GitLab 提交仍缺少 `ChangePassword`、`CompleteRegister`、`ListInventoryLedger` 三个接口实现；当前工作区同样的 `go test ./... -count=1` 和 `go vet ./...` 均通过。故 Go 模块网络故障已修复，GitLab 分支完整同步当前业务代码后才能得到全绿 Go job。

## 5. 数据库迁移

### 迁移前检查

1. 确认目标服务器、实例、数据库名和环境标签。
2. 确认已完成备份并记录备份文件、校验结果和恢复责任人。
3. H16 提供来源-目标对账基线；H15 检查敏感数据和权限边界。
4. 先在隔离测试库执行并记录每个迁移的输出、行数和失败清理结果。
5. 未经授权不得对生产库执行本节命令。

### 推荐顺序

按依赖执行完整文件名，不能只按迁移编号猜顺序：`001_identity`；`002_access_control` 与 `002_patient`；`003_register` 与 `003_register_seed`；`004_order` 与 `004_order_seed`；`005_charge` 与 `005_charge_seed`；`006_inventory` 与 `006_inventory_seed`；`007_dispense`；`008_master`；`009_user_operations_audit`；`010_diagnose`；`011_user_role_scope`；`014_diagnose_permission`；`016_patient_registration_detail`。

目标库保护注意：`016_patient_registration_detail.up.sql` 内含 `USE BHIS`，即使连接参数指定其他库，脚本也会切换到 `BHIS`。隔离测试库不得原样执行该文件；需使用目标专用副本，在副本开头校验 `DB_NAME()` 与预期库名并核对 `dbo.patient` 后再执行。不要用 `-d` 参数代替脚本内的目标库守卫。对应的 down 脚本会删除新增列及其数据，不作为默认回滚步骤。

`012_inventory_batch_readonly`、`015_local_inventory_batch_readonly` 是隔离批次快照用途，不能当成正式库存结构直接部署；`013_idempotency_record` 是否纳入某环境需按对应版本任务卡和目标库核对。启用幂等记录后，收费创建、支付和退费的记录保留 24 小时，过期判断使用服务端 UTC 墙上时钟；应用主机与 SQL Server 主机应保持时间同步，不能用手工修改业务时间代替时钟校准。

项目迁移说明和 `sqlcmd -I`、`QUOTED_IDENTIFIER` 注意事项见 [`migrations/README.md`](../../migrations/README.md)。推荐使用仓库的 `scripts/apply-migration.ps1`，执行前先核对脚本参数和目标库，禁止把口令写在命令行中。

### 迁移后检查

- 目标库结构与迁移版本记录一致。
- `GET /health` 返回正常，驱动显示 `sqlserver`。
- 当前工作区曾在隔离库 `BHIS_PHASE2_TEST_20261015` 运行 `go test ./internal/store/mssql -count=1 -v`，19 项测试全部通过；该证据不覆盖真实 API 进程重启或 24 小时有效期边界。
- H16 核对表数量、关键主键/唯一键、父链和金额/数量汇总。
- H06 执行登录、建档、挂号、开单、收费、发药/退药/退费和权限回归。
- 幂等验收至少覆盖：服务重启后 24 小时内同键重放原结果、同键不同请求返回冲突、过期键删除后进入正常业务状态校验；记录应用主机和 SQL Server 的 UTC 时间、提交 SHA 与测试输出。过期后的支付请求可能因收费单已支付而返回状态冲突，不能把“过期”当成自动重试授权。
- 失败时保留错误输出和回滚证据，不用“脚本未报错”代替对账通过。

## 6. 启动、停止和健康检查

开发/隔离环境可以使用 `go run ./cmd/host -config config.local.yaml start`。交付包使用对应版本的 `b-his-host.exe` 和受控配置启动。Host 应在浏览器打开 `http://127.0.0.1:8888/login`；使用 `Invoke-WebRequest http://127.0.0.1:9999/health` 检查 Go API。启动时 Host 会检查两个端口，只会结束身份、健康状态和端口所有权均验证通过的旧 B-HIS Host；其他占用者不会被结束，Host 会报告冲突并退出。

健康响应至少核对 `status`、`driver`、`contractVersion`、`implementedVersion` 和版本号是否与交付记录一致。前端开发时，Vite 默认使用 `127.0.0.1:8888` 并将 `/api` 代理至 `127.0.0.1:9999`；此时不要同时启动占用相同端口的 Host。

停止前确认没有正在进行的收费、发药、退药或迁移事务。使用 Host 的停止命令或现场批准的服务管理方式停止，随后保存 Host/API 进程状态和端口、`logs/` 中的启动/错误/停止记录、数据库连接、迁移和健康检查结果。不直接删除日志来“清理问题”，按保留策略归档。

## 7. 备份、恢复和回滚

正式环境至少记录数据库完整备份、配置备份、版本包校验和日志归档。备份文件与应用主机分离保存，访问权限最小化。

恢复演练必须在隔离目标库进行，记录恢复开始/结束时间、数据库一致性检查、应用健康检查和抽样业务链。演练不能直接覆盖生产库。

应用回滚步骤：停止新版本入口并保留故障现场日志；确认数据库迁移是否已经执行以及旧版本是否兼容当前结构；按批准的版本包和回滚说明恢复应用；运行 `/health`、登录和只读查询，再决定是否恢复业务入口。

数据库 down 迁移可能删除列、权限或表数据，不能作为默认应急按钮。生产回滚必须使用经过 H03/H16/H17/H01 审核的专用方案，并由用户批准后执行。

## 8. 监控和故障分级

最低监控项包括 `/health` 可用性和响应耗时、Host/API 进程存活、监听端口、SQL Server 连接、应用与数据库 UTC 时钟偏差、请求错误率、慢请求、超时、panic、收费/退费/发药/退药失败数、重复请求冲突、数据库磁盘、日志磁盘、备份结果和连接池压力。

| 级别 | 示例 | 处理 |
|---|---|---|
| P0 | 无法登录、数据错误扩散、重复收费/重复扣库存风险 | 立即暂停相关入口，保留证据，升级 H01/用户 |
| P1 | 核心门诊链持续失败、数据库不可用 | 进入故障处理和回滚评估，H17 牵头，H13 执行获批操作 |
| P2 | 单页面、报表或非核心功能异常 | 记录复现和影响，交 H06/H05/H18 排查 |
| P3 | 文案、布局或说明问题 | 纳入下一版本文档/界面维护 |

## 9. 现场交接验收

交接包至少包含版本号、提交/包校验值、安装路径和配置项清单；数据库实例/库名、迁移清单和 H16 对账结果；Host/API 地址、登录页第一眼、健康检查结果和日志路径；备份策略、恢复演练证据、回滚前提和联系人；H15 安全边界结论、H06 回归结果、H18 操作培训/FAQ；未完成事项、待用户决定事项和明确的接手人。

现场验收不等于用户已批准扩大临床或支付范围；范围变更必须另行确认。

## 10. 维护流程

- 配置、迁移、启动方式、发布包或回滚变化：H13 更新本手册。
- 监控、备份、恢复、容量或事故流程变化：H17 补充并复核。
- 安全和隐私变化：H15 提供结论。
- H01 验收版本和证据，顾书归档备份。
