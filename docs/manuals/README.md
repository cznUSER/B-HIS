## 使用顺序

1. 开发或接口变更先读数据结构文档。
2. 培训和业务验收读操作手册。
3. 安装、升级、运行和故障处理读实施部署手册。

## 版本边界

这些手册描述当前工作区和已有验证证据。它们不等同于生产库已部署、上线已批准或临床/支付政策已确定。生产操作必须以用户授权、H01任务卡和现场验收记录为准。

## 维护规则

- 数据模型、迁移或 API 变化：先由 H03 更新数据结构文档，再由 H01 检查操作/部署影响。
- 页面入口、交互或权限变化：由 H05 提供事实，H18 更新操作手册，H06 复核关键步骤。
- 配置、迁移命令、启动方式、监控或回滚变化：由 H13 更新部署手册，H17 复核运行风险。
- 每次更新都写版本、日期、变更原因和证据路径；顾书负责归档备份。

## H01 文档同步门禁

所有代码、API、数据库、界面、权限、配置、部署、监控、回滚、测试验收口径和用户操作的修改，都必须在同一任务中完成文档影响评估。评估为有影响时，相关手册必须随同交付更新；评估为无影响时，任务回报必须写明 `文档影响评估=无`、检查过的文档和理由。H01 没有同步更新证据或可核验的无影响证据，不得关闭任务、交下一环或报告通过。文档本身修改也要反查其他手册，避免内容冲突。

## H01 GitLab 交付门禁

产生项目文件变更的任务，必须在同一任务完成提交并成功推送到项目 GitLab 远端后，H01 才能关闭任务、交下一环或报告通过。收口时只提交本任务范围内的文件，并记录提交短 SHA、远端、分支、推送时间和结果；不得把其他人的未提交修改、不明文件、凭据或令牌带入提交。推送失败、认证失败、远端不可达或目标分支不明确时，任务保持阻塞/待上传，不得声称完成。纯问答或没有项目文件变更的分析任务，记录 `GitLab同步=不适用` 及理由，不制造空提交。
